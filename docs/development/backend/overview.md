The backend is the server half of the Next.js app: route handlers under `src/app/api` and business code under `src/server`. This guide is the single source of truth for backend conventions.

## Stack

- Node.js runtime on Vercel (route handlers, not Edge, unless a spec says otherwise)
- TypeScript strict, Zod for every input
- Drizzle ORM on Supabase Postgres, migrations by drizzle-kit
- Better Auth for sessions
- Supabase Storage for media (server uses the service role key, never the client)
- Vitest for tests

## Structure

```text
src/server/
├── db/
│   ├── client.ts            # Drizzle client (pooled connection)
│   ├── schema/              # one file per domain + index.ts
│   ├── migrations/          # generated by drizzle-kit, reviewed by hand
│   └── seed/                # catalog seed scripts and data
├── auth/                    # Better Auth config, getSession helper
├── http/                    # handler wrapper, errors, idempotency
├── <domain>/                # workouts, sessions, exercises, plan, share, sync, ai…
│   ├── service.ts           # business logic, takes userId
│   ├── queries.ts           # Drizzle queries, scoped by user
│   ├── errors.ts            # domain error codes
│   └── __tests__/
└── ai/                      # provider client, prompt loader, cost log
```

Files under `src/server` start with `import 'server-only'` where they touch secrets or the database, so a client import fails the build.

## Conventions

- **Always scope by user.** Every query on user data filters by `userId`/`ownerId`. The acting user comes from the session in the handler and is passed down as an argument; services never read global request state. A row the user does not own is reported as not found.
- **Business logic lives in services**, not in route handlers. Handlers parse, authorize, call one service function, map the result.
- **Avoid N+1.** Load related rows with joins or Drizzle's relational `with`, or batch by ids. A list endpoint does a constant number of queries regardless of item count.
- **Write only what changed.** `PATCH` updates only the fields present in the input. Never write back a full row read earlier; another request may have changed a different column meanwhile. See [Database](database.md).
- **Idempotent writes.** Creates use client ids or an `Idempotency-Key`. See `docs/development/request-safety.md`.
- **Edit the domain that owns the behavior.** Do not spread one change across unrelated domains.
- **Validate at the edge, trust inside.** Zod parses input in the handler; services take typed input.

## Configuration

Environment variables are read and validated once in `src/server/env.ts` with Zod. The list of names lives in `.env.example`. Keep personal overrides out of git.
